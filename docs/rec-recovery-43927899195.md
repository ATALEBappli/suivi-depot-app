# REC — établir la publication réelle après le run 43927899195

Le rapport inspect 43930188927 confirme les sources installées et le reçu pending,
mais son compteur de déploiements ne donne ni version publiée ni empreinte du
contenu immuable. Il ne permet donc pas de choisir une récupération sans hypothèse.

Cette correction enrichit uniquement le mode inspect existant lorsque ce reçu
précis est présent. Aucun nouveau workflow, aucune opération d'écriture. Les preuves
source, empreinte, tag et empreinte de sauvegarde sont fixées au run analysé.
La liste des versions est lue sur la route du projet REC et la version créée est
retrouvée par sa description exacte, jamais supposée égale à 2.

Après revue/fusion explicitement autorisée, lancer le workflow existant en inspect
sur main. Le nouveau bloc deploymentRecovery doit contenir publishedVersion,
createdVersion, previousVersion, publishedHash et classification. Aucun ID, URL,
source ou compte n'est ajouté au rapport. Les permissions, la sauvegarde initiale,
le reçu, l'URL conservée et le HEAD sont contrôlés. Toute preuve ambiguë arrête
le diagnostic ; une version tierce est rapportée unexpected_state, jamais acceptée
comme succès. Les sources et la liste des déploiements sont relues en fin de contrôle.
Aucune de ces lectures n'a été exécutée contre Google pendant la préparation.

## Choix de récupération après preuve, autorisation d'écriture distincte

- new_version_published : le contenu publié est celui approuvé et la description
  correspond au run. Ne pas faire de PUT Apps Script, de restore ou de nouveau deploy.
  Adapter la réconciliation du reçu déjà développée à ce run et à cette version
  vérifiée, avec copie privée vérifiée du pending puis finalisation, en conservant
  checkpoint et sauvegarde. La réconciliation version 1 est figée au run #10 :
  ne pas la lancer telle quelle. Cette PR ne modifie pas ce mécanisme d'écriture.
- previous_version_still_published : la version créée par le run contient le bon
  bundle, mais n'est pas publiée. Reprendre sur CETTE version existante, en mettant
  à jour uniquement REC_DEPLOYMENT_ID après une nouvelle sauvegarde et contrôle du
  pending. Ne pas recréer une version, un déploiement ou réinstaller les sources.
  Le deploy actuel ne permet pas cette reprise et refuse un pending ; le restore
  existant n'est envisageable que si l'état correspond exactement à deploymentsBefore
  et si toutes ses validations de sauvegarde passent. Il ne termine pas à lui seul
  cette publication. Préparer le correctif d'écriture uniquement après classification.
- unexpected_state ou refus : geler les écritures et analyser le rapport. Ne jamais
  effacer le reçu pour débloquer, ni substituer un autre projet/déploiement.

La sauvegarde vérifiée et le reçu restent intacts. REFERENTIEL_V2 n'est pas activé.
Les contrôles de concurrence restent séquentiels, non atomiques ; geler les
interventions manuelles et ne pas considérer ce rapport comme une autorisation
permanente. L'erreur initiale peut provenir de la réponse PUT ou du GET suivant :
les anciens logs ne distinguent pas ces deux points. Une classification établit
l'état actuel, pas la cause historique exacte d'une réponse transitoire.

## Correction du contrôle de la sauvegarde brute

Le run inspect 43932432076 s'est arrêté à BACKUP_BASELINE_MISMATCH. Les contrôles
précédents ont donc validé l'empreinte de sauvegarde, sa cible, son contenu, le
pending et l'identité/URL privée du déploiement actuel par rapport au reçu.
Le code ne journalisait pas le sous-test ayant échoué.

checkedBackup conserve state.deployments (réponse REST brute). Le reçu conserve
state.deploymentsState, produit par deploymentState et filtré sur versionNumber
présent. Le contrôle erroné exigeait une seule entrée brute et prenait [0] : un
HEAD non versionné avant ou après l'entrée versionnée suffisait à le faire échouer.
C'est un défaut de représentation démontré sur doublures, pas une preuve que les
ressources Google ont changé. Sans lecture du JSON privé, la présence effective
de HEAD dans cette sauvegarde n'est pas confirmée par les logs disponibles.

Le contrôle corrigé applique le même filtre versionNumber!==undefined, exige
exactement une entrée versionnée et conserve les comparaisons strictes d'ID,
version, projet (champ présent contradictoire refusé), entryPoints et URL/permissions.
La sauvegarde n'est jamais modifiée ou réécrite ; son empreinte épinglée reste
vérifiée avant comparaison. Le rapport indique backupDeploymentCounts (raw,
versioned, unversioned) sans identifiants. En cas de véritable divergence, des
codes distincts COUNT/ID/VERSION/PROJECT/ENTRYPOINTS identifient le champ fautif.

Tests ajoutés : HEAD avant/après, deuxième déploiement versionné, ID/version/projet
contradictoires, URL modifiée, accès public, absence de scriptId et altération de
la sauvegarde après calcul de l'empreinte. Aucune normalisation permissive des
versions ou URLs, aucune écriture Google, aucun relâchement des permissions.
